# CONTEXT_PROTOCOL.md — Token & Context Discipline (the read-the-map law)

> Every role in this framework obeys this. The goal: **spend tokens on the task, not on rediscovering the project.** A role that reads files at random to figure out the stack is a bug — the stack is already written down in the *maps* below. Read the map first; open source only when the map points you there.

## §0 — The three maps (read these, in this order, NOT the whole repo)
1. **`docs/STACK.md`** — what the project is + how to run its gates (the architecture memory map). *Always* the first read.
2. **`docs/INVENTORY.md`** — what already exists to reuse (generated by `gen-inventory.mjs`). Read before writing any new component/util/schema.
3. **The `.claude` checkpoint memory** — where we are + the exact next action (one read = cold resume).

Then, and only then, the **task-specific doc** (one ticket, one DOMAIN section, one DESIGN section). Never pre-read "all of `docs/`."

## §1 — Load budget per role
| Role | Reads (ceiling) | Never reads |
|---|---|---|
| **Orchestrator** (`/system-architect`, `/sprint`) | the 3 maps + the specific tickets in scope | source files (it routes; workers hold heavy context) |
| **Builder** (`/build`, `/db`, `/migrate`, `/notify`) | STACK.md §relevant + INVENTORY + the 1 ticket + the exact files it edits | unrelated apps/packages; other tickets |
| **Reviewer subagents** | the diff (`git diff <base>...HEAD`) + the ticket AC + the one law doc for its lane | the whole tree; files outside the diff unless a finding requires it |
| **Status** (`/team`) | headers/last-3-entries only (see its skill) | source, ever |

## §2 — The rules (enforced, not aspirational)
- **Read the map, not the repo.** If you need a command, a version, a path, or the auth model, it's in `docs/STACK.md`. Don't grep the repo to re-derive it.
- **Read the slice, not the whole.** Use offset/limit or the one section you need. Never read a file "just in case."
- **Never re-read a file you just wrote.** The Edit/Write result already confirmed it.
- **Delegate heavy reading; consume the structured return.** The orchestrator stays thin — subagents/workflows hold the big context and hand back a summary, not raw dumps.
- **Large outputs go to disk, get read once.** Persist migration diffs, screenshots, reports to files; extract what matters; don't echo them back turn after turn.
- **Batch decisions.** One `AskUserQuestion` round beats back-and-forth (which re-loads context each hop).
- **Close early.** After ~3 tickets or a big workflow, checkpoint and start fresh (see `docs/SESSION_PROTOCOL.md`) — a long transcript is ballast once its result is in files.

## §3 — Keeping the maps honest (so the discipline pays off)
The whole scheme only works if the maps are current:
- Regenerate `docs/INVENTORY.md` **before every fan-out** and at close (`node .claude/scripts/gen-inventory.mjs`).
- Update `docs/STACK.md` + `.claude/stack.json` whenever the stack changes (`/stack-change`).
- Update the checkpoint memory at the end of **every** change-making response (this is the resume lifeline — see CLAUDE.md §Memory).

## §4 — Orchestrator fan-out budget (don't burn tokens on a swarm)
Parallelism is **waves**, not a swarm. Hard rule in `/system-architect`:
- **Default cap: 5 concurrent worktree agents.** Anything larger — a bigger fan-out, "one agent per file," a swarm — requires an **explicit `AskUserQuestion` approval first**, stating agent count and why.
- Shared-package changes run **first and alone** (no concurrency). Only file-disjoint work parallelizes.
- Read-only review/QA agents may run in parallel but still count toward the cap for token awareness.
- Prefer **fewer, well-scoped agents** over many thin ones — each agent re-loads the maps, so 10 agents pay the map-load cost 10×.
